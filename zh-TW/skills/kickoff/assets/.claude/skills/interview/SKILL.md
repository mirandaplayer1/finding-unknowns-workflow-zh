# 訪談（Interview）

目的：把「已知的未知」——使用者知道自己還沒想清楚的地方——透過一問一答變成規格。與 /blindspot 分工：盲點掃描找的是使用者沒意識到的問題，訪談處理的是已經浮上檯面的模糊。

## 步驟

1. 讀 `SPEC.md`（特別是未知清單）與 `notes/implementation-notes.md` 的「待確認的未知」，列出所有模糊處。
2. 依影響力排序：**答案會改變骨架的先問**（結構、受眾、範圍、成敗定義），只影響血肉的後問（措辭、細節、樣式）。
3. **選擇訪談形式**：
   - **三題以內、需要追問深究** → 對話模式：一次只問一題，等回答後再問下一題。
   - **四題以上、或題目含選項比較** → 產出「HTML 訪談問卷」（單一自包含檔，存 `notes/`）：每題附「為什麼這題重要、答案會影響什麼」說明、二到四個選項按鈕＋自由填答框＋「還沒想清楚」勾選；底部放「複製答案」按鈕，把作答輸出成結構化文字讓使用者貼回對話。收到答案後逐題回填，「還沒想清楚」的題目轉對話模式降階追問。
   - 兩種形式共同原則：每題說明提問邏輯（他在跟著學怎麼拆解問題）；使用者答不出來時不跳過——降一階問或標記「待原型確認」，交給拋棄式原型處理。
4. 訪談中若發現新的模糊處，加入題目佇列，但總量控制在八題內；超過表示該回去改規格再來。
5. 每題有結論就即時回填 `SPEC.md` 對應章節，訪談結束時更新未知清單狀態，並向使用者摘要：釐清了什麼、還剩什麼；接著建議跑 `/blindspot` 掃出還沒意識到的面向。

## 原則

- 訪談是為了改規格，不是聊天；問不出可回填的答案的題目不要問。
- 優先問「答錯代價高」的：骨架層的誤解在後期修正最貴。
- 使用者的回答若和規格既有內容矛盾，當場指出，一起決定以哪個為準。
- 停損：當剩下的未知「在實作中發現」比「現在用問的」便宜時，停止訪談並說出口——把它們標記為「待實作驗證」記入未知清單，不要問好問滿。
- HTML 產出一律照 WORKFLOW.md〈HTML 產出與互動介面〉：內嵌留言層＋「複製結果」出口（現成片段 `notes/html-comment-layer.html`）。
- 本 skill 到「回填規格、摘要收尾」為止：未經使用者要求，不進入任何實作。
